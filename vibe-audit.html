What this app is

Goal. Ship a dog-rescue fundraising site where promoters get personal donation QRs, donors pay any amount on Stripe, and operators track visits, gifts, and 50% commissions from an admin console.

Who it is for. Public donors; promoters who join for a QR; operators who unlock the employee portal with a shared PIN.

Checks that fit. Public pages, forms (join + admin), private admin area, Stripe payments, Supabase database, avatar uploads, visit geolocation analytics (first-party), outbound Stripe/geo APIs, and a daily operator dashboard. Not needed: blog, marketing email, AI, native apps, cookie-banner analytics vendors, password-account flows (current login is PIN), or visitor UGC feeds.

Fix these first

  1. Compressed images. Replace large originals with compressed WebP, AVIF, or an optimized JPEG or PNG. Workspace: media/hero.mp4 ~38MB and hero-fast.mp4 ~11MB are very large for a first-screen asset; brand PNGs ~95KB.
  2. No secrets in the repo or client bundle. Remove private keys, database passwords, and secret tokens from the repo, its history, and the client bundle. Rotate any secret that was committed. Workspace: js/config.js ships sitePin (shared operator unlock) in the client bundle. Stripe/service secrets stay in .env (gitignored) / Edge secrets — do not paste values.
  3. Protected routes. Check authorization inside the route or server action, and keep signed-out visitors away from private pages. On Next.js, upgrade to a release that fixes the middleware bypass, and keep the check in the route as well. Workspace: admin.html is gated only by client PIN (js/pin-lock.js + sessionStorage). Live Supabase RLS still allows anon ALL on employees/donations/visits, so the private area is not enforced server-side.
  4. Each person can only reach their own data. On every read, update, and delete, check that the record belongs to the signed-in person before you touch it. If the client queries the database, turn on row policies that do the same check. Workspace: Live policies employees_all_anon / donations_all_anon / visits_all_anon / payouts_all_anon use USING true WITH CHECK true for the anon role — any holder of the anon key can read/write all rows.
  5. Sessions expire. End the session after a period of inactivity. A day is a reasonable starting point. Workspace: PIN unlock persists for the tab session with no idle timeout; sessionStorage clears only when the tab is closed.
  6. Account settings. Add a settings page where a signed-in person can see and change the account. Workspace: No account/settings screen for operators or promoters to change PIN, email, or profile beyond admin edit dialogs.
  7. A signed-in person can sign out. Add a sign-out control that ends the session. Workspace: No Sign out / Lock control in admin.html to clear SitePin unlock (sessionStorage pf_site_unlock_v1).
  8. Signup confirms the person is old enough. Add an age confirmation to signup. If the product is for children, collect the parent's consent before you ask the child for anything. Workspace: join.html public signup has no age confirmation checkbox or statement.
  9. The database and file store are not wide open. Keep storage private. Scope each rule to the owner, or serve private files with a signed URL, before you deploy. Leave the service key on the server. Workspace: Live RLS policies grant anon full CRUD on employees, donations, visits, and payouts (confirmed via pg_policies). schema.sql intends to revoke anon table access but production still has open anon policies.
  10. The payment processor allows this business. Read the restricted-business list for the processor you use before you take a live payment. If the product is on that list, get their approval first or leave live charges off. Workspace: Workspace has Stripe integration but no documented confirmation that the Stripe account category allows this fundraising model.
